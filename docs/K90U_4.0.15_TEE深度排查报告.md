> 排查日期：2026-10-02

> 方法：官方内核 vs 自编译内核的 kmsg + logcat 全量差分 + boot 镜像二进制结构对比 + 内嵌 .config 对比

## 一、结论摘要

故障的**唯一根因点**已精确定位到一行代码：

    keystore2: boot_level_keys.rs:120 - In get_level_zero_key: security_level=TRUSTED_ENVIRONMENT
      ↓ 17 毫秒后
    官方内核: super_key.rs:351 - Read keystore.boot_level value BootLevel(30)      ← 成功
    我的内核: raw_device.rs:222 - calling getKeyCharacteristics
              utils.rs:392   - Upgrade failed.
              Error::Km(r#INVALID_ARGUMENT)                                        ← 失败

**KeyMint（TEE 内）对 level zero key 的 getKeyCharacteristics 调用返回 INVALID_ARGUMENT。**
其余症状全部是下游后果：boot stage key 缺失 → super encryption 失败 → Error::Rc(r#LOCKED) → odsign 建不出 HMAC key → CE 存储不可用 → 第三方应用全挂、密码解锁卡死。

**本文档修正了原排查文档的三处判断（见第三节）。**

## 三、对原排查文档的三处修正

### 修正 1：v14 根本没有 SUSFS（H2 的范围要缩小）

原文档把 H2 描述为 KSU/SUSFS 干扰。实测：

- 源码里确实有 SUSFS 补丁（20 个文件：fs/namei.c、fs/exec.c、kernel/sys.c、security/selinux/avc.c 等）
- 但这些调用全部被 #ifdef CONFIG_KSU_SUSFS_xxx 保护（例：fs/namei.c 有 44 处 CONFIG_KSU_SUSFS 保护）
- SukiSU 的 Kconfig 里没有任何 SUSFS 开关 → 这些宏永远为假 → SUSFS 代码编译为空
- 故障内核日志里 susfs 字样出现 0 次

**结论：v14 = KernelSU（含 MANUAL_SU / KSU_DEBUG / KPM），无 SUSFS。H2 只剩「KSU 本身」。**

### 修正 2：打包过程（H0）可以排除

解析四个 boot 镜像（官方 4.0.14 / 官方 4.0.15 / 我的 v14 / AOSP GKI 6.6.142）全部是：

    header_version = 4，header_size = 1584，ramdisk_size = 0，无 bootconfig

现代 Android 的 boot 分区只装内核，ramdisk 在 init_boot、bootconfig 在 vendor_boot。
我的 v14 是把官方 boot.img 的内核原地替换（kernel_size 在偏移 8，内核在偏移 4096），其余字节原封不动，不存在可污染的地方。

### 修正 3：boot 状态不是变量

getprop 显示 verifiedbootstate=green / flash.locked=1，但内核原始 bootconfig（root 读取，模块最难伪造的地方）显示：

    androidboot.verifiedbootstate = "orange"
    androidboot.vbmeta.device_state = "unlocked"

设备实际是解锁状态，那些 green/locked 是 tricky_store + playintegrityfix 模块伪造的（设备上确实装了这两个模块）。所以「官方内核在锁定态测试、自编译内核在解锁态测试」这个潜在混淆因素不存在。

## 五、剩余假设与优先级

| 编号 | 假设 | 依据 | 可能性 |
|---|---|---|---|
| H1 | 内核版本 / 小米私有改动：4.0.15 用户空间依赖 6.6.118+Xiaomi 的某个行为 | v14 在 4.0.8 上正常，4.0.15 才坏，内核没变 | 高 |

**关键推理**：v14 在 **4.0.8** 上完全正常（root、zygisk、13 个模块全可用），升到 **4.0.15** 后 TEE 才坏。
内核一个字节没变 → **变量在用户空间**。所以 H1/H3（用户空间新依赖某个内核特性）比 H2（KSU 干扰）更可能——因为 KSU 在 4.0.8 时代就没有问题。

## KSU 内部机制分析（下一步定位）

KSU 内核侧只有 7 个开关（SukiSU v4.2.0）。v14 相对默认值多开了两个：

| 开关 | 默认 | v14 | 内核侧实际作用 |
|---|---|---|---|
| KSU | y | y | 基础功能，依赖 KPROBES |
| KSU_MANUAL_SU | y | y | 仅影响 ksud/管理器（C 代码里未被引用） |
| KSU_DEBUG | n | **y** | 使 allow_shell 默认 true；启用 debug manager appid；额外日志 |
| KPM | n | **y** | select KALLSYMS_ALL；自述「可能影响系统稳定性」 |

**最可疑的部分：base KSU 的 selinux_hide（36KB 的 feature/selinux_hide.c）**

1. **直接顶掉 SELinux 的 setprocattr 钩子**：
   KSU_LSM_HOOK_INIT(setprocattr, "selinux_setprocattr", my_setprocattr, 0)
   —— 也就是 /proc/self/attr/current|exec|fscreate|keycreate|sockcreate 的处理入口。

2. **拦截 SELinux 文件系统的写入**（my_write_context / my_write_access）：
   用**备份策略** backup_sepolicy 回答权限查询，并把 avd.seqno 写死为 1。
   /sys/fs/selinux/access 正是 libselinux 的 selinux_check_access() 入口。

3. **全局改写 live SELinux policy 的配置位**（故障日志实测）：
   old config: 1  ->  adding POLICYDB_CONFIG_ANDROID_NETLINK_ROUTE
                  ->  adding POLICYDB_CONFIG_ANDROID_NETLINK_GETNEIGH
                  ->  new config: 3221225473

4. 替换 /sys/fs/selinux/status 的 open 处理（伪造 SELinux 状态页）。

**好消息：selinux_hide 是运行时开关**，id 为 KSU_FEATURE_SELINUX_HIDE：

    static bool ksu_selinux_hide_enabled __read_mostly = false;   // 默认关闭
    static const struct ksu_feature_handler selinux_hide_handler = {
        .feature_id = KSU_FEATURE_SELINUX_HIDE, ... };

故障日志里已经出现 selinux_hide 的实际动作，说明**设备上的该开关处于打开状态**。
因此可以在管理器里关闭它后重启来验证，**无需重新编译**。

# 最终结论（2026-10-02 收官）

## 根因：CONFIG_KPM=y

| 配置 | KSU | KSU_DEBUG | KPM | TEE |
|---|---|---|---|---|
| v14 | y | y | **y** | 坏 |
| D2 | y | y | **n** | 正常 |
| D | y | n | n | 正常 |
| A | 无 KSU | — | — | 正常 |

**v14 与 D2 的完整配置差异只有两行**（用 diff 逐行核对过）：

    v14独有:  CONFIG_KPM=y
    v14独有:  CONFIG_LOCALVERSION="-android15-8-wjljh-2026y9m1d2148-4k"
    D2独有:  # CONFIG_KPM is not set
    D2独有:  CONFIG_LOCALVERSION="-android15-8-teeD2-debugonly-4k"

LOCALVERSION 只是版本号字符串，不影响行为。所以：

**KPM 是元凶；KSU_DEBUG 无罪；SUSFS、内核版本、小米私有改动、打包流程全部无关。**

## 机制：结构性副作用，不是 KPM 的运行时行为

用两份日志里都出现的 qseecomd AVC 事件做时间基准（内核 2.635 s <-> logcat 08:49:27.431），把 logcat 时间换算成内核时间：

    keystore / TEE 失败        内核时间  约 3.69 s
    KPM 的唯一活动              内核时间  21.39 s
      [21.386085] kpm: Stub function called (sukisu_kpm_version)

**KPM 的运行代码比故障晚出现 17.7 秒**，说明它没有参与故障。
进一步核实：KPM 目录里没有任何 module_init / initcall（启动期不初始化），
CONFIG_KPM 的全部作用只有三处——把 kpm/compact.o、kpm/kpm.o、kpm/super_access.o 链进内核、
向用户空间报告启用状态、注册 supercall 处理器。

所以触发条件是「KPM 被链接进内核镜像」这个结构性变化（链接顺序 / initcall 次序 / 镜像布局），
而不是它的运行时逻辑。这类副作用难以从静态分析预测，但可以稳定复现。

参考：KALLSYMS_ALL 不是原因 —— 三份配置里它都是 y。

## 可用的最终配置

    CONFIG_KSU=y
    CONFIG_KSU_MANUAL_SU=y
    # CONFIG_KSU_DEBUG is not set
    # CONFIG_KPM is not set

即实验 D（boot_warsaw_6.6.142-teeD-ksudefault.img），已验证：开机正常、进桌面、
第三方应用可打开、TEE 链路完整。

管理器识别不受 KSU_DEBUG 影响 —— is_manager_apk() 用的是编译期宏 KSU_MANAGER_PACKAGE
（apk_sign.c:352-365），与 KSU_DEBUG 无关。

## 编译工具

新增 build_variant.sh，一条命令完成「配置变更 + 增量编译 + 打包 + 校验」：

    ./build_variant.sh <变体名> [--base <基础构建目录>] [--enable SYM]... [--disable SYM]... [--localver <str>]

它从 --base 指定的已完成构建目录复制一份，只重编受影响的文件：实测改 KSU 开关约 100 秒，
而 clean build 约 320 秒。注意：如果本次没有任何真实配置变化（只是重写 .config），
kbuild 会重建 auto.conf 并触发全量重编（约 400 秒），所以迭代时不要无意义地改 LOCALVERSION。
